# 部署模式与本地大模型说明

| 项目 | 内容 |
|---|---|
| 适用系统 | 人工智能学院教学知识库 v1.0.0 |
| 默认模式 | **云端 API 优先**（生产推荐） |
| 可选模式 | 本地离线大模型（演示/断网备用） |
| 编写日期 | 2026-11-17 |

---

## 1. 结论先行

1. **系统默认、生产推荐使用云端 API**：对话用阿里云百炼 `qwen-plus`，向量用 `text-embedding-v2`。速度快（单问约 5～8 秒）、支持多人并发、检索质量更好、运维简单。
2. **本地大模型是可选方案，不是默认方案**：适合无外网演示、数据不出内网的场景；需要一台带 GPU 的工作站，且存在速度、并发、检索覆盖和回答准确率的明显局限。
3. 两种模式通过 `backend/.env` 切换，**代码完全一致**；切换向量模型时必须重建索引（详见第 5.7 节）。
4. 当前线上服务器（2 核 3GB、无 GPU）**无法运行本地模型**，线上必须保持云端模式。

---

## 2. 两种模式对比

| 维度 | 云端模式（默认/推荐） | 本地离线模式（可选） |
|---|---|---|
| 对话模型 | 阿里云百炼 qwen-plus | Ollama + Qwen2.5-7B-Instruct Q4_K_M |
| 向量模型 | text-embedding-v2（1536 维） | BGE-base-zh-v1.5 ONNX（768 维，CPU） |
| 重排 | LLM 重排（qwen-plus） | BGE-reranker-base ONNX（CPU） |
| 硬件要求 | 无（2C3G 云服务器即可） | GPU ≥6GB 显存、内存 ≥16GB |
| 单问耗时 | 约 5～8 秒 | 约 8～15 秒 |
| 并发能力 | 支持多人同时使用 | 单卡单请求，多人会排队 |
| 检索质量 | 较好 | 受语料与 512/768 维限制，部分知识点召回不足 |
| 回答准确率 | 较高 | 7B 模型可能编造 API/函数签名，需核对来源 |
| 网络依赖 | 需要外网与 API Key | 问答链路可完全离线（爬虫子系统仍需外网） |
| 成本 | 按 token 计费 | 零 API 费用，消耗本地算力 |
| 运维 | 简单 | 需维护 Ollama、模型文件、索引重建 |

## 3. 云端模式（默认，生产使用）

`.env` 关键配置：

```ini
LLM_PROVIDER=dashscope
LLM_BASE_URL=https://<百炼工作空间>/compatible-mode/v1
LLM_API_KEY=            # 留空时自动回退 DASHSCOPE_API_KEY
LLM_MODEL=qwen-plus

EMBEDDING_PROVIDER=dashscope
EMBEDDING_MODEL=text-embedding-v2
EMBEDDING_DIMENSION=1536

QUERY_REWRITE_MODE=conditional
```

说明：

- 云端的重排走 LLM（`RERANK_PROVIDER=auto` 自动判断），无需本地重排模型
- 部署脚本 `deploy/deploy.sh` 会自动写入生产安全配置（关闭 DEBUG、生成 JWT 密钥、强管理员密码、开启验证码）

## 4. 本地模式的适用场景与局限

### 4.1 适用

- 教室/实验室无外网或不允许数据出内网的演示
- 需要展示"私有化部署"能力的验收环节
- 云端 API 故障时的临时备用

### 4.2 局限（必须向使用方说明）

| 局限 | 说明 |
|---|---|
| 硬件 | 7B-Q4 模型需约 5GB 显存；低于 6GB 会退化为 CPU 推理，速度骤降 |
| 速度 | 实测单问 8～15 秒；模型未驻留时额外 5～10 秒加载 |
| 并发 | 单卡只能串行处理，多人同时提问会排队 |
| 检索 | I2C/SPI 对比、树莓派 GPIO 等知识点召回不足，回答可能依赖模型通用知识 |
| 准确率 | 示例代码/API 签名可能出错，不能作为权威依据 |
| 索引 | 换向量模型必须全量重建；768 维、2.2 万级分块实测约 68 分钟（4 线程） |
| 磁盘 | 对话模型约 4.7GB，向量/重排模型约 0.4GB，建议放在非系统盘 |
| 运维 | 需要保持 Ollama 服务运行；Windows 重启后需确认服务已启动 |

## 5. 本地模式部署步骤（已在本项目验证）

> 以下步骤为本地工作站（Windows + RTX 3060 6GB）实际执行过的流程，Linux 工作站同理。

### 5.1 硬件与依赖

- GPU：NVIDIA 显存 ≥6GB；内存 ≥16GB；磁盘预留 ≥10GB
- Python 依赖：在云端模式依赖基础上，额外安装 `transformers`（本地 ONNX 分词用）：
  ```bash
  pip install transformers
  ```
- 模型文件目录（建议放在非系统盘）：
  ```
  backend/chroma_data/models/
    bge-base-zh-onnx/          # 768 维向量模型
      model.onnx
      tokenizer.json
      config.json
      tokenizer_config.json
    bge-reranker-base-onnx/    # cross-encoder 重排模型
      model.onnx
      tokenizer.json
      tokenizer_config.json
  ```

### 5.2 安装并配置 Ollama

1. 安装 Ollama 并确认服务运行：`ollama --version`、`ollama list`
2. 设置环境变量（Windows 用户变量 / Linux systemd 环境）：

| 变量 | 值 | 作用 |
|---|---|---|
| `OLLAMA_MODELS` | 如 `E:\ollama-models` 或 `/opt/ollama-models` | 模型目录，避免占满系统盘 |
| `OLLAMA_KEEP_ALIVE` | `30m` | 模型常驻，避免频繁重载 |
| `OLLAMA_NUM_PARALLEL` | `1` | 单卡避免显存分流 |

3. 修改后重启 Ollama 服务

### 5.3 获取对话模型

```bash
# 方式 A：官方仓库（网络好时）
ollama pull qwen2.5:7b-instruct-q4_K_M

# 方式 B：官方仓库速度慢时（本项目实际采用）
# 从 ModelScope 下载单文件 GGUF：Qwen2.5-7B-Instruct-Q4_K_M.gguf（约 4.4GB）
# 存放到非系统盘，例如 E:\ollama-models\gguf\
```

> 注意：官方 Qwen 仓库的 GGUF 可能是多分片文件，Ollama 导入需要单文件，
> 请优先使用单文件仓库（如 lmstudio-community 发布的 Q4_K_M 单文件）。

### 5.4 创建 8k 上下文模型

新建 `Modelfile`：

```
FROM E:\ollama-models\gguf\Qwen2.5-7B-Instruct-Q4_K_M.gguf
PARAMETER num_ctx 8192
PARAMETER num_gpu 99
PARAMETER temperature 0.1
PARAMETER repeat_penalty 1.05
```

执行：

```bash
ollama create qwen2.5-8k -f Modelfile
ollama show qwen2.5-8k     # 确认 parameters 中 num_ctx=8192
```

> 6GB 显存建议 `num_ctx` 不超过 8192；16k 会贴近显存上限，32k 会溢出到 CPU。

### 5.5 下载本地向量/重排模型

- 向量：`BAAI/bge-base-zh-v1.5` 的 ONNX int8 版本（约 102MB）
  - 国内可用镜像 `hf-mirror.com`，仓库 `Xenova/bge-base-zh-v1.5`
  - 需要 `onnx/model_int8.onnx`、`tokenizer.json`、`config.json`、`tokenizer_config.json`
- 重排：`BAAI/bge-reranker-base` 的 ONNX int8 版本（约 279MB）
  - 仓库 `onnx-community/bge-reranker-base-ONNX`
  - 重命名为 `model.onnx` 放入上述目录

### 5.6 修改 `backend/.env`

```ini
# 对话：本地 Ollama
LLM_PROVIDER=local
LLM_BASE_URL=http://localhost:11434/v1
LLM_API_KEY=ollama
LLM_MODEL=qwen2.5-8k
LLM_MAX_TOKENS=768

# 向量：本地 ONNX（768 维）
EMBEDDING_PROVIDER=onnx_bge
EMBEDDING_MODEL=bge-base-zh-v1.5
EMBEDDING_DIMENSION=768
EMBEDDING_LOCAL_MODEL=<项目绝对路径>/backend/chroma_data/models/bge-base-zh-onnx

# 重排：本地 cross-encoder（auto 在本地模式自动启用）
RERANK_PROVIDER=auto
RERANK_MIN_SCORE=0.0

# 本地模式省去查询改写的一次 LLM 调用
QUERY_REWRITE_MODE=off
```

> 切换向量模型后**必须重建索引**，否则向量维度不匹配，检索为空。

### 5.7 重建索引

```bash
cd backend
python rebuild_indexes.py
```

- 脚本会自动：按 `(document_id, chunk_index)` 去重 → 备份旧索引 → 重新向量化 → 重建 FAISS + BM25
- 实测：22,468 个分块、768 维、4 线程、512 token 截断约 **68 分钟**
- 重建期间建议停止后端服务（脚本会先改名旧索引）
- 重建完成后重启后端

### 5.8 启动与验证

```bash
python -m uvicorn app.main:app --host 0.0.0.0 --port 8001
```

验证清单：

1. `curl http://127.0.0.1:8001/api/health` 返回 `{"status":"ok"}`
2. 登录后提问「ESP32 如何连接 Wi-Fi？」，应有来源并正常作答
3. 提问「今天天气怎么样？」应立即拒答（域外问题拦截）
4. `nvidia-smi` 确认模型显存占用正常；`ollama ps` 确认模型处于运行状态

### 5.9 回滚到云端模式

1. 恢复 `backend/.env` 的云端配置（第 3 节）
2. **恢复与云端向量维度一致的索引**：
   - 若保留云端索引备份：直接还原 `chroma_data/faiss_index` 与 `bm25_index.pkl`
   - 否则执行 `python rebuild_indexes.py`，用云端嵌入重新生成 1536 维索引（会产生 API 费用）
3. 重启后端，确认 `[Embedding] provider=dashscope`、`[LLM] provider=dashscope`

## 6. 本地模式实测数据（本项目）

| 测试项 | 结果 |
|---|---|
| 模型显存占用 | 4.99GB / 6GB（8k 上下文完整驻留 GPU） |

| 天气类问题 | 0 秒拒答 |
| 索引重建 | 22,468 分块 / 768 维 / 68 分钟 |
| 后端回归测试 | 153 项全部通过 |

## 7. 风险提示

1. 本地模式**不能替代**云端模式作为学校正式服务；建议仅在演示或断网场景启用
2. 本地 7B 模型会编造 API 名称/参数，教学使用必须核对来源
3. 本地模式换向量模型/重建索引期间服务不可用，需安排维护窗口
4. 本地模型目录、自定义模型名（`qwen2.5-8k`）属于机器相关配置，换机需按第 5 节重建
5. 若同时在本机运行后端与 pytest，16GB 内存可能出现内存不足，测试前请先停服务
