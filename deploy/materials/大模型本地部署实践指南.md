# 大模型本地部署实践指南：Ollama 与 vLLM

> 本文是「视频专区 · 大模型部署」栏目的配套学习资料，覆盖从硬件评估、模型量化、Ollama 快速上手到 vLLM 生产级服务化的完整路径。看视频建立直觉，本文用于查参数、查命令、排查问题。

## 一、先判断你的硬件能跑多大模型

部署前先估算显存，避免下载完模型才发现跑不起来。一个够用的粗略公式：

```
显存需求 ≈ 参数量 × 每参数字节 + KV Cache + 框架开销（约 1~2 GB）
```

每参数字节随精度变化：

| 精度 | 每参数字节 | 7B 模型权重大致占用 |
| --- | --- | --- |
| FP16 / BF16 | 2 | 约 14 GB |
| INT8 | 1 | 约 7 GB |
| INT4（Q4 量化） | 约 0.5 | 约 3.5~4 GB |

常见规模的经验值（INT4 量化、单轮短上下文）：

| 模型规模 | 最低可用显存 | 建议显存 | 典型场景 |
| --- | --- | --- | --- |
| 1.5B~3B | 4 GB | 6~8 GB | 教学演示、文本分类 |
| 7B~8B | 6 GB | 8~12 GB | 个人助手、问答 |
| 14B | 10 GB | 16 GB | 质量更好的通用问答 |
| 32B | 20 GB | 24~32 GB | 复杂推理、代码生成 |
| 70B | 40 GB 以上 | 多卡 | 企业级推理 |

注意两点：

1. KV Cache 随上下文长度线性增长。上下文从 4K 提到 32K，KV Cache 可能翻几倍，是长文档场景的主要显存来源。
2. 消费级显卡（如 RTX 4060 8G、3060 12G）适合 7B~14B 的 INT4 量化模型，不建议勉强跑 FP16。

## 二、量化格式怎么选

| 格式 | 代表工具 | 优点 | 注意 |
| --- | --- | --- | --- |
| GGUF（Q4_K_M、Q5_K_M） | llama.cpp / Ollama | CPU/GPU 混合推理，门槛最低 | 高并发吞吐一般 |
| AWQ | vLLM / AutoAWQ | GPU 推理快，精度损失小 | 需要匹配模型与 CUDA 环境 |
| GPTQ | GPTQ-for-LLaMa 等 | 生态成熟、模型多 | 不同实现兼容性需验证 |
| FP8 | vLLM（新卡） | 接近 FP16 质量 | 需要 Hopper/Ada 等新架构支持 |
| bitsandbytes | Transformers | 改造成本低 | 吞吐不如专用引擎 |

选择原则：单机个人使用优先 GGUF + Ollama；对外提供 API 且有并发要求，用 vLLM + AWQ/FP8。

## 三、Ollama：十分钟跑通第一个本地模型

### 3.1 安装与验证

1. 从官网下载对应平台安装包并完成安装。
2. 终端验证：

```bash
ollama --version
ollama serve        # 后台服务未自动启动时手动启动，默认端口 11434
```

### 3.2 拉取与运行模型

```bash
ollama pull qwen2.5:7b          # 拉取模型（首次较大，注意磁盘空间）
ollama list                     # 查看本地已有模型
ollama run qwen2.5:7b           # 进入交互式对话
ollama run qwen2.5:7b "用三句话解释什么是 RAG"
```

### 3.3 HTTP 接口调用

Ollama 原生接口：

```bash
curl http://localhost:11434/api/chat -d '{
  "model": "qwen2.5:7b",
  "messages": [{"role": "user", "content": "介绍一下 vLLM"}],
  "stream": false
}'
```

Ollama 同时提供 OpenAI 兼容接口，可直接复用现有 SDK：

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")
resp = client.chat.completions.create(
    model="qwen2.5:7b",
    messages=[{"role": "user", "content": "用一句话说明 Ollama 的作用"}],
)
print(resp.choices[0].message.content)
```

### 3.4 常用环境变量

| 变量 | 作用 |
| --- | --- |
| `OLLAMA_HOST` | 监听地址，如 `0.0.0.0:11434` |
| `OLLAMA_MODELS` | 模型存储目录，避免默认装到 C 盘 |
| `OLLAMA_KEEP_ALIVE` | 模型驻留时间，默认 5 分钟，短了会频繁重载 |
| `OLLAMA_NUM_PARALLEL` | 并行请求数，显存不足时保持默认 |

## 四、vLLM：对外提供推理服务

Ollama 适合个人开发验证；需要并发、稳定吞吐时用 vLLM。它通过 PagedAttention 管理 KV Cache，并支持连续批处理，显存利用率明显更高。

### 4.1 启动 OpenAI 兼容服务

```bash
pip install vllm

python -m vllm.entrypoints.openai.api_server \
  --model Qwen/Qwen2.5-7B-Instruct \
  --served-model-name qwen-rag \
  --host 0.0.0.0 --port 8000 \
  --gpu-memory-utilization 0.85 \
  --max-model-len 8192 \
  --tensor-parallel-size 1
```

### 4.2 关键参数说明

| 参数 | 含义 | 建议 |
| --- | --- | --- |
| `--gpu-memory-utilization` | 允许 vLLM 占用的显存比例 | 0.8~0.9，留出系统余量 |
| `--max-model-len` | 最大上下文长度 | 按业务真实需要设置，越长越吃显存 |
| `--tensor-parallel-size` | 张量并行卡数 | 单卡填 1，多卡填 GPU 数量 |
| `--quantization` | 量化方式 | awq / gptq / fp8，需与权重匹配 |
| `--max-num-seqs` | 同时处理的请求数 | 并发高而显存紧时适当降低 |

### 4.3 调用服务

```bash
curl http://localhost:8000/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "qwen-rag",
  "messages": [{"role": "user", "content": "vLLM 的 PagedAttention 解决什么问题？"}]
}'
```

```python
from openai import OpenAI

client = OpenAI(base_url="http://localhost:8000/v1", api_key="EMPTY")
print(client.chat.completions.create(
    model="qwen-rag",
    messages=[{"role": "user", "content": "解释连续批处理"}],
).choices[0].message.content)
```

### 4.4 Docker 方式

```bash
docker run --gpus all -p 8000:8000 \
  -v /data/models:/models \
  vllm/vllm-openai:latest \
  --model /models/Qwen2.5-7B-Instruct \
  --gpu-memory-utilization 0.85
```

## 五、服务化与安全底线

把推理服务放到内网供业务系统调用时，至少做到：

1. 前面加一层网关（Nginx / APISIX），由网关统一校验 API Key、限流、记录调用日志。
2. 推理端口只监听内网地址，不要直接映射到公网。
3. 为每个业务方分配独立 Key，便于审计与吊销。
4. 配置健康检查：定时请求 `/v1/models`，失败时告警。
5. 监控显存与请求队列，观察 `nvidia-smi` 与 vLLM 日志中的排队时长。
6. 模型文件、Key 不进入 Git 仓库；部署脚本里使用环境变量注入。

## 六、常见问题排查

| 现象 | 常见原因 | 处理 |
| --- | --- | --- |
| 启动即 OOM | 模型精度过高或上下文过长 | 换 INT4/AWQ 权重，降低 `--max-model-len` |
| 首次响应特别慢 | 首次加载权重、编译 kernel | 预热一次请求，保持服务常驻 |
| 并发一高就超时 | 显存或并发上限不足 | 降低 `--max-num-seqs`，或增加副本 |
| 输出乱码或截断 | 编码设置、最大 token 太小 | 统一 UTF-8，调大 `max_tokens` |
| 端口被占用 | 旧进程未退出 | 查找进程并结束，或换端口 |
| Ollama 模型反复加载 | `OLLAMA_KEEP_ALIVE` 太短 | 调大驻留时间 |
